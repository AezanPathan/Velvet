# Velvet v0.1 Readiness Review

Date: 2026-04-13

## Verdict

**Yes — this is good enough for a `0.1` release** if you position it as an early/preview release for developers.
The feature set already feels meaningful: scene graph, WebGL backend, Blazor host, glTF loading, animation, lighting, skybox, and particles.

## What is strong today

1. **Architecture is clean and understandable.**  
   `Velvet.Core` (domain/contracts) -> `Velvet.Graphics.WebGL` (backend) -> `Velvet.Hosting.Web` (host/orchestration) is a solid separation.
2. **Build health is good.**  
   Engine solution builds, TS/Webpack bundle builds, and `Velvet-Site` builds.
3. **Runtime guard rails are present.**  
   Host API uses null checks and clear invalid-state exceptions (`ThrowIfRunning`, camera/program checks, etc.).
4. **Scope is already compelling for 0.1.**  
   You are not shipping only a triangle demo; you have real engine behaviors and sample scenes.

## Refactor items I recommend

### Priority for v0.1 release quality

1. **Finish/contain material migration noise.**  
   `Velvet-Site` currently builds with obsolete `Material` warnings from the compatibility alias in `Velvet.Core.Rendering.Materials.Material`.  
   For 0.1, either:
   - migrate demos to the new type(s), or
   - keep compatibility but ensure docs/examples use the non-obsolete API only.
2. **Align release/version identity.**  
   WebGL package metadata is `"version": "1.0.0"` while planned release is `0.1`.  
   Align package versions and release tags to avoid user confusion.
3. **Promote demo app build into normal validation flow.**  
   `Velvet-Site` is not in `Velvet.sln`, so solution builds can miss app-level breakages.  
   Include it in the solution or always build it in CI.

### Good next refactors after 0.1

1. **Reduce global bridge state (`JsBridge`).**  
   Global mutable bridge config is convenient but can become fragile as host options grow.
2. **Host cleanup error handling should be explicit.**  
   `VelvetHost.CleanupResizeInteropAsync` intentionally swallows `JSDisconnectedException` and `ObjectDisposedException`; consider minimal logging hooks for diagnosability.
3. **Clarify or remove empty `ServiceExtensions`.**  
   Empty public surface can confuse users about intended registration patterns.
4. **Add basic automated tests (at least smoke tests).**  
   There are currently no test files; a small baseline suite would improve confidence for public releases.

## Suggested release framing

Ship `0.1` as:

- **"Preview / early adopter"**
- API may evolve, but core architecture and rendering path are stable
- targeted scenarios: WebGL + Blazor scene rendering with glTF/material/lighting/particles

This framing matches the current maturity very well.
